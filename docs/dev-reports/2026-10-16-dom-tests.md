## 2. vitest 配置改动

### 2.1 保留 `environment: "node"`，DOM 测试用 per-file 覆盖

`vitest.config.ts` 中原本 `environment: "node"` 是因为纯函数测试无需 jsdom。为了不改动现有 297 个测试的运行时行为，我们让 DOM 测试通过文件顶部注释单独指定 jsdom 环境：

```ts
// @vitest-environment jsdom
import ...
```

这样：
- 现有 297 个测试继续走 node 环境，性能不变；
- 新增 DOM 测试走 jsdom，功能不受影响；
- 无需在 `vitest.config.ts` 里写 include/环境的分支规则。

### 2.2 `vitest.setup.ts` 加载 jest-dom matcher

```ts
import "@testing-library/jest-dom/vitest"
```

`@testing-library/jest-dom/vitest` 扩展了 vitest 的 `expect`，让所有测试都能使用 `toBeInTheDocument()` 等断言。对纯函数测试无副作用。

### 2.3 `vitest.config.ts` 无需改动

`setupFiles: ["./vitest.setup.ts"]` 已配置，直接使用即可。

## 6. 遗留问题与说明

1. **ImageEditor 的编辑/导出阶段未覆盖**：ImageEditor 内部通过 fabric.Canvas + ReactCrop 管理裁剪→编辑→导出状态，且阶段切换依赖 `setStage()`（无外部 API 触发）。当前的 7 个测试覆盖了上传阶段的完整渲染与初始禁用态；若要覆盖裁剪比例按钮、编辑工具（文字/形状/滤镜）、导出按钮，需要：
   - 在 ImageEditor 上暴露一个可测试的 `setStage` 或类似 hook（改动生产代码），或
   - 在测试中 mock `useDropzone` 直接触发 `onDrop`（需 mock React dropzone 内部状态），或
   - 通过 `initialUrl` + mock `fetch` + mock `FileReader` 走完 crop 阶段（可行但繁琐）。
   
   当前选择保守方案（只测上传阶段稳定渲染），避免引入过多 mock。

2. **PlanBadge 的 4 分钟轮询未测试**：`POLL_INTERVAL_MS = 4 * 60 * 1000` 会污染测试时间，未覆盖。可用 `vi.useFakeTimers()` 单独验证。

3. **jsdom 环境性能**：新增 DOM 测试整体运行时间从 297 个测试的 ~1s 增加到 336 个的 ~16s（DOM 渲染开销）。若后续测试规模继续增长，可考虑：
   - 只对真正的交互测试用 `@vitest-environment jsdom`（当前已采用此策略）；
   - 或使用 `@vitest-environment-edge` / 更轻量的 DOM mock。

4. **ImageEditor 的重依赖（fabric / react-dropzone / ReactCrop）**：这些库在 jsdom 下会有 canvas 兼容问题。当前用 mock 方案绕过；未来若需真实交互测试，建议引入 `@happy-dom` 或升级到 jsdom 的 canvas 支持。
