## 背景

2026-10-16 至 10-22 期间，`cloud_service/billing/` 下完成了支付宝 OpenAPI + 微信支付 APIv3 的真实对接（`87d3110` `16b4cee` `6a44015`），包括退款端点、日终对账、订单超时关闭。上线时暴露：

1. **主体资质**：本项目尚无对公支付宝商户、微信支付商户号；测试走的是沙箱，无法承载真实收款。
2. **合规成本**：支付牌照、发票、退款纠纷流程、财务对账系统，远超单人/小微团队承受范围。
3. **运营重心错位**：真正需要投入的是账号体系、feature gate、注册码签发，不是支付通道。

**证据**：
- `docs/handover/PROJECT-HANDOVER.md` §1.4「支付」行：「平台支付已彻底删除」
- `docs/handover/PROJECT-HANDOVER.md` §4「支付删除」行、§7.2 决策「不做」
- `git show --stat 889b3ec`：删 `cloud_service/billing/alipay.py` `weixin_pay.py` `refund.py` 等

## 决策

**彻底删除平台支付代码**，商业闭环收敛为「个人微信收款 → 用户手动联系 → 后台人工签发注册码 → 客户端离线验签激活」。

**具体落地**：
- `889b3ec`：删 `cloud_service/billing/` 下支付宝、微信、退款端点、对账任务、订单超时关闭全部代码
- `60ea8e9`：官网用个人微信二维码替换原占位图（P5=B，见 ADR-0003 关联说明）
- `6879212`：P0 修 `feature_gate` 漏 `import select` 导致的 Pro 用户静默降级（支付删除后判档全靠注册码 + 订阅）
- `312e4ba`：`NOTICE.txt` 第 3 行版权署名 `maning636`（P2=A）

## 否掉了什么

| 方案 | 为什么否 |
|---|---|
| 保留支付代码，走沙箱 | 沙箱不承载真实收款，代码留着只是维护负担；用户误触会产生真实订单 |
| 走 Stripe / PayPal 海外通道 | 中国大陆用户支付成功率极低，且需海外收款主体 |
| 走第三方支付聚合（连连/汇付天下） | 仍要资质与对公账户，运营复杂度不减 |
| 保留支付宝/微信测试代码但不下发注册码 | 支付链路本身仍要维护，退款、对账任务仍是运维负担 |
| 用户自助充值 + 自动发码 | 无支付通道时无法自动核销，注册码需 Ed25519 私钥签发，人工环节无法省略 |

## 代价

**收益**：
- 零支付通道成本（无商户费率、无对账系统、无发票流程）
- 商业化路径清晰：个人微信收款 → 人工发码 → 客户端激活
- 删除代码量 > 500 行，减少长期维护面

**代价**：
- 支付规模受限于人工操作速度（发码、发链接、备注订单）
- 无法提供自动化的发票、退款、订阅到期提醒
- 客户端需要处理「支付失败但已付款」的对账场景，用户可能因此反复联系

**已知副作用**：
- 若未来用户量增长到需要自动发码，需重新引入支付通道 + 幂等发码器
- 财务对账依赖微信交易记录的人工导出

## 未来复审触发条件

- 单月付费用户数 > 50，人工发码成为瓶颈
- 用户反馈「找不到订单」「无法退款」投诉率上升
- 引入独立运营方托管收款
