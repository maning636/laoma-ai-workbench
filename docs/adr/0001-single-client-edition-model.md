# ADR-0001: 商业分层改单一客户端 + 注册码∩订阅判档

- **状态**：已接受（补录）
- **日期**：2026-10-23
- **决策者**：马哥（产品拍板）+ 工作组（实施）
- **证据分级**：【已验证】

---

## 背景

项目早期（2026-10-19 起）采用「Community / Pro 双安装包」分层：官网挂两套下载入口，客户端各自独立分发。到 2026-10-22 收官时，此结构暴露三个问题：

1. 官网两个下载入口互相干扰，且两版之间的功能差异需人工在文档里维护，出现 `24bbbdd` 与 `512236c` 之间 Community 版文件被误删的事故。
2. `e6c1925` 修 `latest.yml` 名字不匹配的根因排查中发现，两套产物在 electron-builder 的 `artifactName` 与 `latest.yml` 生成链路上互相踩踏。
3. 升级路径复杂：Community → Pro 只能靠重下、重装、重装账号凭据，用户流失点极高。

**证据**：
- `docs/handover/PROJECT-HANDOVER.md` §4「单一客户端」行、§2.1 下载入口只剩一套、§3.1 版本轨迹 1.1.4 = `e6c1925`
- `git show --stat e6c1925`：删掉 `desktop-electron/dist-community/` 相关脚本

## 决策

**收敛为单一安装包**：官网只挂一个下载入口，客户端内按**本地注册码 ∩ 云端订阅**的双轨交集派生最终档位（「完整版」或「限制功能版」），激活切换就地生效，无需重装。

**具体落地**：
- `d264d4f`：客户端分级改读本地交集，补 `plan` 派生与 12 项 `feature_gate` flag
- `e6c1925`：合并为单一客户端，删独立 Community 打包链路 + 修 `latest.yml` 名字不匹配根因
- `2f59d05`：`build-package.bat` 改纯 ASCII，出客户端发布形态待决表 D1–D5

## 否掉了什么

| 方案 | 为什么否 |
|---|---|
| 保留双安装包并行 | 官网两个入口相互干扰；Community→Pro 升级路径复杂；构建链路互相踩踏 |
| 只按云端订阅判档 | 云端订阅体系尚未完成商业化配置（P7=B，L1-1 云端 LLM key 未提供），单依赖云端判档会让 Pro 用户降级 |
| 只按本地注册码判档 | 判档模型另一半（12 项 flag、`max_accounts`、`max_platforms` 等）被砍掉，商业化能力退化 |
| 引入硬件指纹授权 | 5–8 人日，见 `authorization-vs-registration.md`；现阶段注册码已足够 |

## 代价

**收益**：
- 官网下载入口从 2 减到 1，营销页面与验收清单大幅简化
- 用户激活后无需重装，账号、cookie、素材目录全部保留
- 打包链路单一，`latest.yml` 名字匹配问题根因消失

**代价**：
- 前端与客户端必须正确处理判档失败态（注册码非法/过期 + 订阅降级 两种情况）
- 客户端需要联网读取云端订阅；离线态下判档走本地注册码兜底

**已知副作用**：
- 已发布的 1.1.1 / 1.1.2 / 1.1.3 版本仍是双版形态，1.1.4 起才是单一版
- 官网旧版 1.1.4 三件套需在 `_superseded_round18/` 归档，`Prism-Fusion-source.zip` 必须绑定 `f36c620` 而非 HEAD

## 未来复审触发条件

- 用户反馈云端订阅降级带来的判档切换体验问题（例如：降级后无法回退）
- 云端订阅系统正式对外运营（`CLOUD_LLM_API_KEY` 已配置、订阅计费上线）
- 需要引入硬件指纹授权时（触发 `authorization-vs-registration.md` 路线）
